# Эпизоды и API Forte Vision v4

Дата: 18 октября 2026. **Экспериментальный прототип: не развёрнут и исключён из рабочего кода из-за пропусков положительных видео.** Ниже сохранён дизайн эксперимента; он не описывает текущий production. Выбранное отдельное обновление — [v3.1](SOURCE_CONTRACTS_V3_1_2026-10-18.md).

## Что изменилось

Требования разделов 4–7 и 10 кейса допускают несколько возможных нарушений и человеческую проверку. Одна ссылка на правила или положительный класс JEPA не должны превращать обычное действие в нарушение. Новая обработка разделяет наблюдение действия, наличие визуального повода для проверки и подбор нормативного источника.

JEPA-LGBM-FULL остаётся первым детектором. Отрицательный класс пропускает Qwen и RAG. При положительном Qwen3-VL-8B получает обзор видео и кадры около примерного момента. Она возвращает видимые факты, функциональную роль участника, название действия, причину проверки и одну из внутренних оценок: `possible_risk`, `routine`, `unclear`. Эти оценки не являются дополнительными вердиктами API и не доказывают юридическое нарушение.

Если обзор не даёт понятного рискованного действия либо содержит неразборчивый эпизод, существующий второй проход используется как уточняющая визуальная проверка. Для него разрешение изображений выше. Число проходов не увеличивается. Невидимые условия закона не должны сами по себе делать видимое действие неразборчивым.

Обычные разборчивые действия не передаются в RAG. Если после визуальной проверки остались только обычные действия с подтверждёнными наблюдениями, результат — `no_violation`. Неразборчивость, все неизвестные факты, сбой декодирования или модели остаются ошибкой обработки. Неизвестные условия закона не подменяются отрицанием и не являются технической ошибкой сами по себе.

## Отдельные события вместо рейтинга из трёх кандидатов

`backend/events.py` объединяет повторные наблюдения до вызова RAG по действию, функциональной роли и близости времени. Дополнительный контекст не создаёт ещё одно событие. Действия кассира и инкассатора не сливаются по одному только совпадению времени. Сохраняются ссылки на исходные кадры; противоречащие факты не стираются.

Жёсткого ограничения «всего три события» больше нет. Текущие два визуальных прохода возвращают максимум четыре кандидата, а уточняющий проход — максимум один. В RAG передаются все отдельные принятые кандидаты; API сортирует результат по времени, а не по вероятности. Отдельного поля «основное нарушение» нет.

Дедупликация остаётся эвристикой: похожие действия одной роли с разницей менее шести секунд могут быть объединены. Разреженные кадры не дают надёжных границ каждого события. Нельзя обещать обнаружение всех коротких или повторяющихся действий.

## Нормативный контекст

Сохранены гибридный BM25/BGE-M3 поиск, RRF внутри каждого уровня, структурные parent–child единицы и полные родительские пункты с зависимостями. Документы, веса и индексы не расширяются ради этого изменения.

Перед нейронным выбором действует дополнительная проверка явной области операции. Например, глава о сопровождении клиента не выбирается только на основании наличия денег; нужны наблюдения сопровождения. Для главы об инкассации нужны соответствующие наблюдения. Заведомо противоположные направления выдачи/приёма также отфильтровываются. Причина исключения каждого кандидата сохраняется в приватной диагностике.

Эти фильтры не заменяют полную проверку применимости нормы. Неизвестные роли и исключения остаются неизвестными. При отсутствии точного пункта допустим документ-контекст с явной отметкой `context_only`, но только для эпизода, уже прошедшего отдельный визуальный отбор. Нейтральное действие не становится событием из-за найденного документа.

Тип события берётся из названия видимого действия Qwen, а не из номера найденного пункта. RAG получает факты и роли; оценка JEPA, score и внутренняя визуальная классификация ему не передаются как факты.

## Генерация и JSON

В обоих нейронных декодерах согласованы разрешённый алфавит и EOS. Для русского и казахского текста явно включён кириллический диапазон. У Qwen штатная конфигурация перечисляет два токена завершения; ограниченный JSON-декодер ориентируется на токен токенизатора. Другой токен завершения подавляется, чтобы он не обрывал JSON внутри строки.

Выбор источника ограничен ID переданных пунктов, строк и фактов. Объяснение имеет JSON-схему и отдельный смысловой валидатор. Дорогая regex-грамматика для текста объяснения в production не используется. Длина проверяется схемой и валидатором; неизвестные ссылки, числа и категоричные обвинения отклоняются.

Валидатор отличает вопрос «проверить, не нарушил ли» от утверждения «нарушил». Упоминание номера допускается только как ссылка на точно выбранный пункт. Номер другого пункта или неподтверждённое числовое утверждение по-прежнему не принимаются. Если генерация не проходит, используется учтённое шаблонное объяснение, без выдумывания наблюдений и источников.

Модели не заменялись: визуальная Qwen3-VL-8B и текстовая Qwen3-VL-4B остаются BF16. Бюджеты входа — 24576 и 8192 соответственно. Это ограничения приложения, не нативные окна моделей.

## API

Эндпойнты жюри прежние: `POST /api/v1/analyze` с multipart-полем `file` и `GET /api/v1/jobs/{job_id}`, оба с `X-API-Key`. Отдельные браузерные маршруты сохраняют проверку сессии и изоляцию заданий.

`backend/contracts.py` описывает `processing`, `done`, `failed` в OpenAPI. Успешный ответ имеет только два значения `verdict`; список `violations` должен соответствовать вердикту. Для события обязательны тип, неотрицательный таймкод, описание и 1–3 кадра. Ошибка не может нести чистый вердикт.

Дополнительные поля сохранены для совместимости. Полные тексты идут в `rule.quote` и `rule.context`, а в обязательный `description` код добавляет краткое название источника, точный пункт при наличии и официальный URL. Поэтому источник доступен даже клиенту, игнорирующему дополнительные поля. Внутренняя пометка `insufficient` не является третьим пользовательским вердиктом.

Gzip включается только по стандартному `Accept-Encoding: gzip`. Декомпрессированный JSON и JPEG совпадают с несжатым ответом. На прежнем сохранённом положительном ответе размер уменьшился с 567211 до 405512 байт (28.5%); это измерение размера, не обещание такого же ускорения сети. Качество кадров не снижалось.

Старые завершённые задания не пересчитываются. Чтобы увидеть v4, нужно загрузить видео заново.

## Проверки и ограничения

В staging прошли 58 backend-тестов и 135 RAG-тестов. Полные видео-прогоны и фактический деплой будут внесены после завершения проверки. Первые неуспешные экспериментальные прогоны не засчитываются как успешные.

Обе головы LightGBM и локализатор обучены на всех 40 видео. Проверки на них — функциональный smoke, не независимый test, не CV и не новая оценка F1. Корректные JSON, хэши и ссылки не доказывают правильность восприятия Qwen, выбора нормы или обоснованность каждого события. Новый ракурс и неизвестные категории отдельно не подтверждены.

Один GPU worker сохраняет очередь и дедлайн 285 секунд. Несколько принятых запросов делят ресурс; надёжность SLA под произвольной нагрузкой не подтверждена. Точные предельные время и качество требуют отдельного набора новых видео и испытания нагрузки.

Изменения находятся в `backend/`, тестах и `patches/legal-rag-mvp-v1/`; исходные пакеты моделей не редактируются. Коммиты и push не выполняются.
